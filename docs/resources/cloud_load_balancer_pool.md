# gcore_cloud_load_balancer_pool (Resource)

Load balancer pools group backend instances with a load balancing algorithm and health monitoring configuration.

Manage the pool's health monitor with the
`gcore_cloud_load_balancer_pool_health_monitor` resource.

## Example Usage

### TCP pool with health monitor and session persistence

Creates a TCP pool on port 80 with cookie-based session persistence, and adds
PING health checks with a separate health monitor resource.

```terraform
resource "gcore_cloud_load_balancer_listener" "tcp_80" {
  project_id = 1
  region_id  = 1

  load_balancer_id = gcore_cloud_load_balancer.lb.id

  name          = "My first tcp listener with pool"
  protocol      = "TCP"
  protocol_port = 80
}

resource "gcore_cloud_load_balancer_pool" "tcp_80" {
  project_id = 1
  region_id  = 1

  load_balancer_id = gcore_cloud_load_balancer.lb.id
  listener_id      = gcore_cloud_load_balancer_listener.tcp_80.id

  name         = "My first tcp pool"
  protocol     = "TCP"
  lb_algorithm = "ROUND_ROBIN"

  session_persistence = {
    type        = "APP_COOKIE"
    cookie_name = "test_new_cookie"
  }
}

resource "gcore_cloud_load_balancer_pool_health_monitor" "tcp_80" {
  project_id = 1
  region_id  = 1

  pool_id = gcore_cloud_load_balancer_pool.tcp_80.id

  type        = "PING"
  delay       = 10
  max_retries = 5
  timeout     = 5
}
```

### Proxy protocol pool

Creates a pool using the PROXY protocol with least-connections algorithm on port 8080.

```terraform
resource "gcore_cloud_load_balancer_listener" "proxy_8080" {
  project_id = 1
  region_id  = 1

  load_balancer_id = gcore_cloud_load_balancer.lb.id

  name          = "My first proxy listener with pool"
  protocol      = "TCP"
  protocol_port = 8080
}

resource "gcore_cloud_load_balancer_pool" "proxy_8080" {
  project_id = 1
  region_id  = 1

  load_balancer_id = gcore_cloud_load_balancer.lb.id
  listener_id      = gcore_cloud_load_balancer_listener.proxy_8080.id

  name         = "My first proxy pool"
  protocol     = "PROXY"
  lb_algorithm = "LEAST_CONNECTIONS"
}
```

### Nested Schema for `members`

Required:

- `address` (String) Member IP address
- `protocol_port` (Number) Member IP port

Optional:

- `admin_state_up` (Boolean) Administrative state of the resource. When set to true, the resource is enabled and operational. When set to false, the resource is disabled and will not process traffic. Defaults to true.
- `backup` (Boolean) Set to true if the member is a backup member, to which traffic will be sent exclusively when all non-backup members will be unreachable. It allows to realize ACTIVE-BACKUP load balancing without thinking about VRRP and VIP configuration. Default is false.
- `monitor_address` (String) An alternate IP address used for health monitoring of a backend member. Default is null which monitors the member address.
- `monitor_port` (Number) An alternate protocol port used for health monitoring of a backend member. Default is null which monitors the member `protocol_port`.
- `subnet_id` (String) `subnet_id` in which `address` is present. Either `subnet_id` or `instance_id` should be provided
- `weight` (Number) Member weight. Valid values are 0 < `weight` <= 256, defaults to 1. Controls traffic distribution based on the pool's load balancing algorithm:
  - `ROUND_ROBIN`: Distributes connections to each member in turn according to weights. Higher weight = more turns in the cycle. Example: weights 3 vs 1 = ~75% vs ~25% of requests.
  - `LEAST_CONNECTIONS`: Sends new connections to the member with fewest active connections, performing round-robin within groups of the same normalized load. Higher weight = allowed to hold more simultaneous connections before being considered 'more loaded'. Example: weights 2 vs 1 means 20 vs 10 active connections is treated as balanced.
  - `SOURCE_IP`: Routes clients consistently to the same member by hashing client source IP; hash result is modulo total weight of running members. Higher weight = more hash buckets, so more client IPs map to that member. Example: weights 2 vs 1 = roughly two-thirds of distinct client IPs map to the higher-weight member.

## Migrating from the `healthmonitor` attribute

Earlier releases managed the health monitor through a nested `healthmonitor`
attribute on this resource. That attribute is removed. The health monitor now
has its own resource, `gcore_cloud_load_balancer_pool_health_monitor`.

The upgrade does not delete the monitor. The pool keeps it, and Terraform stops
tracking it. To manage it again, do these steps in one apply:

1. Remove the `healthmonitor` block from the pool.
2. Add a `gcore_cloud_load_balancer_pool_health_monitor` resource with the same
   settings.
3. Add an `import` block that adopts the existing monitor. The import ID is the
   pool's ID: `<project_id>/<region_id>/<pool_id>`.

```terraform
resource "gcore_cloud_load_balancer_pool" "example" {
  # ... pool settings, without the healthmonitor block
}

resource "gcore_cloud_load_balancer_pool_health_monitor" "example" {
  project_id = 1
  region_id  = 1

  pool_id = gcore_cloud_load_balancer_pool.example.id

  type        = "HTTP"
  delay       = 10
  timeout     = 5
  max_retries = 3
}

import {
  to = gcore_cloud_load_balancer_pool_health_monitor.example
  id = "1/1/${gcore_cloud_load_balancer_pool.example.id}"
}
```

The plan shows the monitor as imported, with no create and no delete. If the
settings differ from the existing monitor, the plan shows an in-place update.
A different `type` replaces the monitor. You can remove the `import` block
after the apply.

A configuration that still sets `healthmonitor` on the pool fails to plan with
an "Unsupported argument" error.


## Import

Import is supported using the following syntax:

```shell
$ terraform import gcore_cloud_load_balancer_pool.example '<project_id>/<region_id>/<pool_id>'
```

The import ID is slash-separated: `<project_id>/<region_id>/<pool_id>`.

~> `listener_id` and `load_balancer_id` are read back from the pool's
`listeners` and `loadbalancers` relationships, so either may be omitted. A
configuration naming the listener and load balancer that import recorded
(the first of each list) imports with a clean plan.

A pool can be the default pool of several listeners. L7 policies on other
listeners can also redirect traffic to it. A configuration naming any other
listener in `listeners` plans a one-time in-place update that records that
listener. No field is sent to the API, and the pool is not replaced.

The API does not show whether a listener uses the pool as its default pool or
only through an L7 policy. Name a listener that uses the pool as its default
pool. If the pool is replaced later, the new pool is created with the configured
`listener_id`. An omitted `listener_id` is not sent.

Changing either ID to a listener or load balancer that the pool is not attached
to replaces the pool. The API cannot move an existing pool to another parent.
Refresh records only a listener or load balancer that the API reports for the
pool. A configured ID that the pool is not attached to, including one already
in state, therefore plans a replacement.
