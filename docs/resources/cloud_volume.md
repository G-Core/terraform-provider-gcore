# gcore_cloud_volume (Resource)

Volumes are block storage devices that can be attached to instances as boot or data disks, with support for resizing and type changes.

## Example Usage

### Boot volume from image

Creates a boot volume from an OS image.

```terraform
# Create a boot volume from an image
resource "gcore_cloud_volume" "boot_volume" {
  project_id = 1
  region_id  = 1
  name       = "my-boot-volume"
  source     = "image"
  image_id   = "6dc4e521-0c72-462f-b2d4-306bcf15e227"
  size       = 20
  type_name  = "ssd_hiiops"
  tags = {
    environment = "production"
  }
}
```

### Standalone data volume

Creates a blank data volume for additional storage.

```terraform
# Create a standalone data volume
resource "gcore_cloud_volume" "data_volume" {
  project_id = 1
  region_id  = 1
  name       = "my-data-volume"
  source     = "new-volume"
  size       = 50
  type_name  = "standard"
}
```

### Volume restored from a snapshot

Restores a volume from a snapshot. The size comes from the snapshot, so it does
not have to be declared.

```terraform
# Restore a volume from a snapshot. The size comes from the snapshot, so it does
# not have to be declared.
resource "gcore_cloud_volume" "restored_volume" {
  project_id  = 1
  region_id   = 1
  name        = "my-restored-volume"
  source      = "snapshot"
  snapshot_id = "88f3e0bd-ca86-4cf7-be8b-dd2988e23c2d"
  type_name   = "standard"
}
```

-> **`size` is required for every source except `snapshot`.** A volume created
with `source = "new-volume"` or `source = "image"` must declare a `size`; only a
snapshot restore derives it. Once the volume exists the size is tracked in state,
so removing `size` from the configuration is a no-op — set a larger value to
resize.

## Import

Import is supported using the following syntax:

```shell
$ terraform import gcore_cloud_volume.example '<project_id>/<region_id>/<volume_id>'
```

~> **One adopting apply is needed after import.** The API does not return
`source`, `image_id`, `snapshot_id`, `attachment_tag` or
`instance_id_to_attach_to`, so the first apply after import records the values
from your configuration into state without changing the volume; the plan shows
an update-in-place and a warning naming the attributes. `image_id` and
`instance_id_to_attach_to` are checked against what the API reports and a
contradiction fails the apply; the others are trusted as-is, so check them
first. `type_name` is read from the API, so omitting it keeps the recorded
value; write the lowercase value the API reports (`standard`, not
`Standard`): a value that differs only in case fails validation at plan
time. After that apply, changing or
removing `source`, `image_id`, `snapshot_id`, `attachment_tag` or
`instance_id_to_attach_to` plans a replacement; use `terraform apply
-replace=` to recreate the volume with different values. A configuration
that could not create the volume (`source = "image"` without `image_id`,
`source = "snapshot"` without `snapshot_id`, `attachment_tag` without
`instance_id_to_attach_to`) is rejected at plan time whenever the relevant
values are known and the plan would create or replace the volume, and warned
about otherwise. The adoption window closes on the successful adopting apply,
or on the second refresh after import; the plan warns while it is open. After
a command-mode import, an apply that fails after refresh but before this volume
update runs may cause the next run to plan replacement. Retry with `terraform
apply -refresh=false`, or remove the resource from state and import it again. A
configuration `import` block survives one such failed apply and can retry
adoption on the next run. Excluding `source` from the plan with `lifecycle {
ignore_changes = [source] }` after import leaves
`source` unrecorded and, together with a no-op `terraform apply
-refresh=false` (which does not refresh), keeps the window open until the
next refreshing apply; a later plan that would record any of the other four
attributes while `source` is ignored is refused - remove `source` from
`ignore_changes` so the adopting apply records them together, or use
`-replace=`.
